# 07. 마이그레이션 로딩 (로컬 → 원격) — 신규/미래 설계안

> ⚠️ **이 문서는 아직 구현되지 않은 to-be 화면의 설계안이다.** 현재 코드에는 서버 원격 DB로의 데이터 이전 로직도, 이 로딩 화면도 없다.
> 관련 데이터/네트워크 자산: `Dependencies/CoreNetwork`, `PersistencesService`, `AuthService`(`TokenClient`).
>
> 🔄 **아래 "전체 화면 모달" 안은 [0002 결정 6](../decisions/0002-diary-sync-engine.md)에서 상단 플로팅 토스트로 뒤집혔다.**
> 로컬 데이터가 이미 완전히 사용 가능하고 서버 데이터에 의존하는 화면이 아직 없어, 첫 실행을 통째로 막을 이유가 없다는 판단이다.
> 이 문서의 진행률·재시도·카피에 대한 의도는 토스트에도 그대로 유효하다. 전체 화면으로 되돌리려면 `AppFeature.Route`에 `.migrating`을 더하면 되고 엔진과 상태는 재사용된다.

## 목적
현재 러닝 일기는 로컬 SwiftData에만 저장된다. 향후 일기 데이터를 서버 원격 DB로 옮겨, 앞으로는 서버 통신으로 일기를 가져오도록 전환한다. 그 **최초 전환(로컬 → 원격 업로드)이 진행되는 동안** 사용자에게 진행 상황을 보여주고 조작을 막는 **로딩/전환 화면**이 필요하다.

### 왜 만드는가
- 마이그레이션은 네트워크·데이터양에 따라 수 초~수십 초가 걸릴 수 있고, 중간 종료 시 데이터 정합성이 깨질 위험이 있다.
- 사용자에게 "지금 데이터를 안전하게 옮기는 중"임을 알리고, 실패 시 재시도 경로를 제공해야 한다.
- 서버 전환 이후의 첫 진입 경험이므로 신뢰감 있는 UX가 중요하다.

## 진입 / 이탈 (제안)
- **진입 조건**: 최초 서버 전환이 필요한 사용자에 한해 1회. 판정 로직(예: 로컬에 미업로드 레코드 존재 && 서버 마이그레이션 미완료 플래그) 필요.
  - 배치 위치 후보: `AppFeature.Route`에 `.migrating` 케이스 추가 → `.loading` 세션 판정 후, `.main` 진입 전에 분기.
- **이탈**:
  - 성공 → 마이그레이션 완료 플래그 저장 → `.main`(주간 기록)으로 진입.
  - 실패 → 재시도 UI 유지(메인 진입 차단) 또는 "나중에" 선택 시 로컬 모드로 임시 진입(정책 결정 필요).

## 화면 구성 (UI) — 제안
전체 화면 모달(다른 조작 차단). 위→아래로:

### 1) 상태 일러스트/타이틀
- [목적] "데이터를 옮기는 중"이라는 안심 메시지.
- [정보 위계] 1차.
- [제안] 러닝 감성에 맞는 일러스트/애니메이션 + "기록을 안전하게 옮기고 있어요" 류 카피.

### 2) 진행률 표시
- [목적] 얼마나 남았는지, 멈춘 게 아님을 전달.
- [정보 위계] 1차.
- [제안] 결정적 진행률(업로드한 레코드 수 / 전체 수) 프로그레스 바 + "N / M개" 텍스트. 총량 파악이 어려우면 단계 인디케이터(준비 → 업로드 → 검증 → 완료)로 대체.

### 3) 보조 안내
- [목적] 중단 방지·소요 안내.
- [제안] "앱을 닫지 말아 주세요", 예상 소요 힌트. 저전력/네트워크 경고.

### 4) 실패 상태
- [목적] 실패 시 회복.
- [제안] 실패 사유(네트워크/서버) + [다시 시도] 버튼(+ 선택적 [나중에]). 부분 성공 시 이어서 업로드(멱등).

## 기능 / 인터랙션 (제안)

| 동작 | 결과 |
|------|------|
| 화면 진입 | 미업로드 로컬 레코드 수집 → 배치 업로드 시작, 진행률 갱신 |
| 업로드 진행 | 레코드/배치 단위 진행률 반영(고빈도 갱신은 로컬 상태로 throttle) |
| 성공 | 완료 플래그 저장 → 메인 진입 |
| 실패 | 에러 상태 전환, [다시 시도]로 실패 지점부터 재개 |

## 선행 조건 (기술 전제)
이 화면을 구현하려면 **화면 UI 외에 서버 마이그레이션 파이프라인이 신규로 필요**하다. 현재 자산 기준 정리:

### 이미 존재해 재사용 가능
- **원천 데이터**: 로컬 저장은 단일 테이블 `RunningRecordPersistenceModel`(평탄화 구조)이라 서버 DTO 매핑이 단순하다. `Diary.toDomain()` 결과를 업로드 단위로 사용 가능.
- **레코드 식별자**: `Diary.id: UUID`가 있어 서버 upsert 키(멱등성)로 활용 가능.
- **인증 스택**: `TokenClient`(키체인 accessToken) + `AuthClient`(소셜 로그인)가 이미 동작 → 마이그레이션 API 인증에 재사용.
- **HTTP 클라이언트**: `CoreNetwork.shared.request(_:)` + `RequestAPI` 프로토콜 존재. snake_case 자동 인코딩/디코딩 지원.

### 신규로 필요
- **러닝 기록 업로드 API**: 현재 `RequestAPI` 실사용은 `GET /api/v1/shoes`뿐. `Endpoint`에 러닝 기록 엔드포인트가 없음 → POST/배치 업로드 `RequestAPI` 신설.
- **마이그레이션 오케스트레이션**: 미업로드 수집 → 배치 전송 → 재시도/부분성공 처리 → 완료 플래그. (신규 Client/Feature)
- **진행률·상태 모델**: 전체/완료 카운트, 단계, 에러 상태.
- **진입 판정·완료 플래그 저장소**: "마이그레이션 완료" 영속 플래그.

### 정리 필요(부채)
- **baseURL 키 이원화**: `CoreNetwork`는 Info.plist `APIBaseURL`, `AuthService`는 `API_BASE_URL`을 사용한다. 서버 통합 확장 전에 키를 통일하는 것이 안전하다.

## 데이터 요약

| 항목 | 소스/상태 |
|------|-----------|
| 업로드 원천 | `RunningRecordPersistenceModel`(로컬) / `Diary` |
| upsert 키 | `Diary.id: UUID` |
| 인증 | `TokenClient`/`AuthClient` (기존) |
| 전송 | `CoreNetwork` + 신규 업로드 `RequestAPI` |
| 완료 판정 | 신규 영속 플래그 |

## 구현 상태
- ❌ 로딩/전환 화면 UI 전체 미구현
- ❌ 서버 업로드 API·마이그레이션 오케스트레이션 미구현
- ❌ 진입 판정/완료 플래그 미구현
- 🧹 baseURL 키 이원화 정리 선행 권장
- ✅ (선행 완료) 인증 스택·HTTP 클라이언트·평탄화된 로컬 스키마·레코드 UUID는 이미 존재
