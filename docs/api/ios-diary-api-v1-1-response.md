## 2. 수용 항목

### 2.1 인코딩 후 body 크기 제한 (§2.3)

**서버안을 그대로 수용한다.**

- `JSONEncoder` 결과의 `Data.count`를 전송 직전에 확인한다.
- 4.5MiB를 초과하면 route를 순서 보존 균등 샘플링으로 추가 축약한 뒤 재인코딩한다.
- `routeOriginalPointCount`는 **최초 원본 개수**를 유지한다(추가 축약 전 값이 아니라 다운샘플 이전 원본).
- 추가 축약이 일어나면 `routeSamplingMethod`는 `uniform`이다. 원본이 50,000점 이하여서 `none`이었더라도 이 시점에 `uniform`으로 바뀐다.
- `413`을 받으면 동일 payload를 재시도하지 않는다.

> 이 항목은 §2.1과 충돌한다. [3.1장](#31-idempotency-key--v1에서-도입하지-않기를-제안)에서 다룬다.

### 2.2 러닝 타입 출처 (§3.2 중 `runningTypeSource`)

**필드 도입을 수용한다.** 다만 enum 값은 정정이 필요하다 → [3.5장](#35-runningtypesource-enum-값-정정)

### 2.3 총 에너지의 결측 의미 (§3.3)

**수용한다.** 기초대사 값을 얻지 못하면 `totalEnergyBurned`를 `null`로 보낸다.

```json
"activeEnergyBurned": 512.4,
"totalEnergyBurned": null
```

- 현재 구현은 `활동 칼로리 + (기초대사 ?? 0)`이라 기초대사 부재 시 활동 칼로리와 같은 값이 나갔다. 이를 `null`로 바꾼다.
- `activeEnergyBurned`는 기존 **`0` = 미측정** 관례를 유지한다(§1에서 서버가 `null` 정규화하기로 한 그 관례).
- 따라서 `activeEnergyBurned: 0` + `totalEnergyBurned: null`은 "둘 다 미측정"을 뜻한다.

### 2.4 날씨 원시값 확장 (§3.5)

**표시용 카테고리 대신 원시 수치를 보내고 분류는 재계산 가능하게 한다**는 방향에 전적으로 동의한다. 앱도 같은 방향으로 정리 중이다.

- `apparentTemperature`(°C), `cloudCover`(0~1)는 **이미 WeatherKit 조회 시 받고 있다.** 분류에만 쓰고 버리던 것을 보존해 전송하도록 바꾼다.
- 수집 가능 OS 범위: 앱 최소 지원이 **iOS 18.0**이고 WeatherKit은 iOS 16.0부터이므로, **전 지원 기기에서 수집 가능하다.** 별도 분기가 필요 없다.
- `precipitationIntensity`만 확인이 필요하다 → [4장 2번](#4-확인-요청)

### 2.5 오류 코드 분기 (§4)

**응답 계약의 5개 조합을 그대로 처리한다.**

| HTTP | `detail.code` | 앱 처리 |
|---|---|---|
| `401` | 없음 | 토큰 갱신 후 1회 재시도, 실패 시 재로그인 |
| `409` | `WORKOUT_ALREADY_EXISTS` | **성공 동기화로 간주**하고 중복 업로드 중지 |
| `413` | 없음 | route 추가 축약 후 새 body로 재시도, 동일 payload 재시도 금지 |
| `422` | `SHOE_NOT_FOUND` 또는 검증 상세 | 신발 동기화 또는 payload 수정 후 재시도 |
| `5xx` | — | 동일 body 재시도 |

> `IDEMPOTENCY_KEY_REUSED`는 [3.1장](#31-idempotency-key--v1에서-도입하지-않기를-제안)의 역제안이 수용되면 발생하지 않는다.

한 가지 요청이 있다. 현재 앱의 네트워크 계층이 오류 응답 body를 버리고 상태 코드만 전달해서 `detail.code`를 읽을 수 없다. **이 부분은 클라이언트가 고칠 작업**이며 진행 예정이다. 서버 쪽 변경은 필요 없고, 다만 **오류 body 형태(`detail.code`의 정확한 JSON 경로와 타입)를 확정해 알려주면** 디코딩 타입을 맞추겠다.

## 3. 역제안 항목

### 3.1 `Idempotency-Key` — v1에서 도입하지 않기를 제안

> 서버 요청 §2.1

**키가 body에서 파생되므로 새 정보가 없다.**
제안된 키는 `diary-{workout.id}`이고 `workout.id`는 이미 body 최상위에 실린다. 서버가 §1에서 확정한 **"동일 사용자의 동일 `workout.id`는 409로 거절"** 규칙이 같은 값으로 이미 동작하므로, 헤더는 같은 판정 근거를 한 번 더 옮겨 적는 것에 가깝다.

**재시도 시나리오를 409가 이미 커버한다.**
오프라인 큐·타임아웃 재전송에서 서버가 이미 저장한 상태라면 `409 WORKOUT_ALREADY_EXISTS`가 돌아온다. 그리고 §4 표가 그 경우의 앱 처리를 **"성공 동기화로 간주하고 중복 업로드 중지"**로 이미 규정했다. 즉 `200 + idempotencyReplayed: true`와 `409 WORKOUT_ALREADY_EXISTS`는 **응답 형태만 다를 뿐 앱의 후속 동작이 동일하다.**

**제거하면 §2.3과의 충돌이 함께 사라진다.**
키는 `diary-{workout.id}`로 고정인데, §2.3은 413 이후 route를 더 줄인 **다른 body**로 재시도하라고 한다. 서버 규칙상 이는 "동일 키 + 다른 body"이므로 `409 IDEMPOTENCY_KEY_REUSED`가 되어, 두 요구가 정면으로 부딪힌다. 키를 두지 않으면 이 예외 설계 자체가 불필요해진다.

**비용은 서버에 남는다.**
키 저장·SHA-256 해싱·재사용 판정·키↔body 대조 로직이 필요한데, 위 이유로 얻는 것이 없다.

> **회신안**: v1에서는 `Idempotency-Key`를 도입하지 않고 **`workout.id` 기반 409 중복 방지만 유지한다.**

한계도 밝혀둔다.

- 향후 **수동 입력 기록**(HealthKit 유래가 아닌 다이어리)을 전송하게 되면 `workout.id`가 없어 멱등 판정 근거가 사라진다. 다만 그때는 `diary-{workout.id}` 형태 자체도 성립하지 않으므로 **키 설계를 새로 해야 하며, 지금 도입해도 그 시나리오를 커버하지 못한다.**
- 수정(PUT)·삭제처럼 `workout.id`로 자연 멱등이 되지 않는 엔드포인트가 생기면 그때 도입하는 편이 낫다.

서버가 그래도 유지를 원한다면 클라이언트는 헤더를 보낼 수 있다(추가 비용이 작다). **그 경우에 한해** §2.3 충돌 해소가 필요하다.

- **(a) 413 재시도에 한해 키 재사용 예외** — 선호
- (b) 키에 body 해시 포함 (`diary-{workout.id}-{bodyHash8}`)

(a)를 선호하는 이유는 4.5MiB 사전 축약으로 413 자체가 드물고, (b)는 정상 재시도의 멱등성까지 함께 약화시키기 때문이다.

### 3.2 `schemaVersion` — 보내지 않는 쪽을 제안

> 서버 요청 §2.2

**서버가 이미 부재를 정의했다.**
§2.2가 "현재 서버는 필드가 없으면 `1`로 처리한다"고 밝혔다. 앱이 이 필드를 생략해도 서버 해석은 어긋나지 않는다. 즉 이 요청은 "없으면 깨진다"가 아니라 "명시해주면 좋겠다"에 가깝다.

**버전 협상 수단으로서 실효가 없다.**
클라이언트가 보내는 값은 앱 빌드에 박힌 상수다. 서버가 실제로 알아야 하는 "이 요청이 어떤 계약인가"는 **body 스키마 자체가 이미 드러낸다** — `runningTypeSource`가 있으면 신버전이고 없으면 구버전이다. 상수 필드는 그 정보를 중복 서술할 뿐이다.

**오히려 틀릴 수 있는 필드다.**
상수 리터럴이라 계약을 바꾸면서 이 값 갱신을 잊으면 **body 내용과 자기 선언이 어긋난다.** 그 순간 서버는 어느 쪽을 믿을지 알 수 없어, 없는 것보다 나빠진다.

**엔티티 미러링 원칙의 예외가 늘어난다.**
[요청 스키마 문서](./create-diary-request.md)는 "엔티티에 존재하지 않는 필드는 이 계약에 포함하지 않는다"를 원칙으로 세웠고 예외는 다운샘플 메타데이터(`routeOriginalPointCount`·`routeSamplingMethod`) 2개뿐이다. `schemaVersion`은 세 번째 예외가 되는데, 위 이유로 그 대가에 값하지 않는다.

**계약 버저닝은 이미 경로가 하고 있다.**
엔드포인트가 `POST /api/v1/running-logs`다. 호환되지 않는 변경은 경로(`/api/v2/`)로 가르는 편이 표준적이고, body 필드와 경로가 각자 버전을 주장하면 이중 관리가 된다.

> **회신안**: 앱은 `schemaVersion`을 보내지 않고 서버의 **"부재 = 1"** 규칙에 의존한다. 호환 불가 변경은 URL 경로 버전으로 가르자.

반론도 밝혀둔다.

- 같은 엔드포인트에서 **점진적 필드 추가**를 서버가 명시적으로 분기하려면, 필드 유무 추론보다 버전 상수가 안전하다는 주장은 성립한다. 특히 "필드가 있는데 `null`"과 "필드 자체가 없음"을 구분해야 할 때다.
- 다만 [3.3장](#33-timezonesource-대신-timezone을-nullable로)의 nullable `timeZone`에서 그 구분이 실제로 필요해지지는 않는다. 구버전 앱은 폴백 때문에 `timeZone`을 **항상 문자열로** 채워 보내므로, `timeZone: null`이 오면 그 자체가 신버전 신호다.

같은 엔드포인트에서의 버전 분기 설계를 이미 확정했다면 **상수 한 줄이라 추가는 언제든 가능하다.** [4장 3번](#4-확인-요청)에 답을 주면 반영하겠다.

### 3.3 `timeZoneSource` 대신 `timeZone`을 nullable로

> 서버 요청 §3.1

문제 인식에는 **전적으로 동의한다.** "`timeZone`만으로는 운동 당시 위치 기준인지 업로드 시점 기기 기준인지 알 수 없다"는 지적이 정확하다. 다만 해법으로는 다른 안을 제시한다.

#### 산출 가능한 값이 2개뿐이다

제안된 4값 중 클라이언트가 만들어낼 수 있는 값은 둘뿐이다.

| 제안 값 | 산출 가능 여부 |
|---|---|
| `workoutLocation` | **불가**. 좌표→타임존 역산에 오프라인 API가 없다. `CLGeocoder.reverseGeocodeLocation`이 유일한 경로인데 네트워크 의존·요율 제한이라 전송 경로에 넣기 어렵다 |
| `deviceAtWorkout` | 가능. `HKMetadataKeyTimeZone`이 바로 이 값이다 |
| `deviceAtUpload` | 가능. 메타데이터가 없을 때의 폴백 |
| `unknown` | 발생하지 않음. 폴백이 항상 성립한다 |

한 가지 정정이 필요하다. **`HKMetadataKeyTimeZone`은 "운동 위치로 계산한 값"이 아니다.** 기록 기기가 워크아웃 저장 시 남기는 IANA identifier이므로 의미상 `deviceAtWorkout`에 해당한다. 즉 지금 우리가 1순위로 쓰는 값조차 `workoutLocation`이 아니다.

결국 제안된 4값 enum은 실질적으로 **1비트**가 된다.

#### 그런데 그 1비트는 진짜 문제의 증상이다

현재 구현은 타임존을 모를 때 기기 현재값(`TimeZone.current`)으로 채워 **모르는 값을 아는 값처럼** 전송한다. 해외에서 기록한 러닝이라면 **틀린 타임존이 참값으로 저장된다.**

그리고 메타데이터 부재는 드문 일이 아니다.

| 기록 출처 | `HKMetadataKeyTimeZone` |
|---|---|
| Apple Watch 워크아웃 앱 | **있음** |
| 서드파티 앱(Strava·Nike Run Club·Garmin 등)이 HealthKit에 기록 | **없음** |
| 건강 앱 수동 입력 | **없음** |

러닝 앱 특성상 서드파티 기록 비중이 작지 않으므로, 폴백은 예외가 아니라 **상시 발생하는 경로**다.

#### 회신안

`timeZoneSource`를 신설하는 대신 **`timeZone`을 nullable로 바꾼다.**

```json
"timeZone": "Asia/Seoul"   // 운동 당시 기기가 기록한 값 (신뢰 가능)
"timeZone": null           // 기록 당시 타임존을 알 수 없음
```

- 필드 하나로 source enum과 **동일한 정보량**을 전달한다.
- 서버에 **거짓값이 저장되지 않는다.**
- 폴백 정책 소유권이 서버로 넘어간다. 서버가 사용자 프로필 타임존 등으로 폴백하되 **그것이 자기 폴백임을 안다.** 클라이언트가 폴백하면 서버는 그 사실을 영원히 알 수 없다.
- 앱 내부 표시는 기존대로 기기 타임존으로 대체하므로 UI 영향이 없다.

이 안에서도 §3.1이 든 활용처(현지 날짜, 주간 통계, 연속 러닝)는 그대로 달성된다. `timeZone`이 있으면 신뢰하고, `null`이면 서버 폴백값으로 계산하되 신뢰도를 낮춰 표시하면 된다.

> 서버가 그래도 enum 형태를 선호한다면 **`deviceAtWorkout | deviceAtUpload` 2값**으로 수용 가능하다. 다만 그 경우에도 `workoutLocation`과 `unknown`은 산출할 수 없다.

### 3.4 `runningType: "unknown"` — 도입하지 않기를 제안

> 서버 요청 §3.2 중 `unknown`

**추론 실패를 outdoor로 강제하는 경로가 없다.** 판별 로직은 다음과 같다.

1. `HKMetadataKeyIndoorWorkout`이 있으면 그 값을 따른다.
2. 없으면 워크아웃의 **총 거리**로 판별한다. 거리가 `0`이면 `treadmill`, 아니면 `outdoor`.

즉 경로나 거리 기록이 없는 경우는 **`outdoor`가 아니라 `treadmill`로 떨어진다.** 우려하신 "추론 실패를 outdoor로 강제"가 발생하지 않는다.

반면 `RunningType`에 `unknown`을 추가하면 러닝 타입 라벨·트레드밀 분기 등 **앱 표시 로직 전반**이 영향을 받는다. 그리고 서버가 얻으려던 "이 값이 추론인가"는 아래 `runningTypeSource`만으로 판별할 수 있다. 추론값을 `unknown`으로 버리는 것보다 **최선의 추측을 유지하면서 그것이 추측임을 표시하는 편**이 정보량도 많다.

> **회신안**: `runningType`은 `outdoor | treadmill` 이분법을 유지하고, 추론 여부는 `runningTypeSource`로 전달한다.

### 3.5 `runningTypeSource` enum 값 정정

> 서버 요청 §3.2 중 source enum

제안: `healthKit | routeInference | user | unknown`
회신: **`healthKit | distanceInference`**

| 제안 값 | 판정 |
|---|---|
| `healthKit` | **유지**. `HKMetadataKeyIndoorWorkout` 기반 |
| `routeInference` → **`distanceInference`** | 2순위 근거는 경로 유무가 아니라 **워크아웃의 총 거리**다. 이름을 실제 근거에 맞춘다 |
| `user` | **제외**. 러닝 타입을 사용자가 직접 지정하는 UI가 없다. 향후 도입 시 추가 |
| `unknown` | **제외**. [3.4장](#34-runningtype-unknown--도입하지-않기를-제안)에 따라 발생하지 않는다 |

```json
"runningType": "treadmill",
"runningTypeSource": "distanceInference"
```

### 3.6 `userShoeId` — 전제 정정 후 별도 과제로 분리

> 서버 요청 §3.4

먼저 `shoeId`의 의미에 상호 오해가 있어 정정한다.

**`shoeId`는 이미 "서버 카탈로그에서 받은 `Shoe.id`" 그 자체다.** `GET /api/v1/shoes`로 받은 값을 그대로 실어 보낸다. 다만 신발 API 도입 이전 버전에서 **하드코딩된 신발 목록으로 저장된 기록**이 남아 있어, 앱이 다이어리를 저장하기 전에 그 문자열을 카탈로그와 매칭해 `Shoe.id`로 옮긴다. 매칭되는 신발이 없으면 `null`로 보낸다.

따라서 `shoeId: null`의 사유는 두 가지다.

1. 사용자가 신발을 선택하지 않았다.
2. 구버전 기록인데 카탈로그에서 매칭되는 신발을 찾지 못했다.

이는 [요청 스키마 문서](./create-diary-request.md)의 "신발" 절에 적은 내용과 같으며, **"카탈로그 모델 ID"라는 표현이 오해를 부른 것으로 보인다.**

그 위에서 §3.4를 보면, **앱에는 "같은 모델 두 켤레"를 구분하는 사용자 소유 신발 인스턴스 개념 자체가 없다.**

- `Shoe`는 서버 카탈로그를 그대로 받는 읽기 전용 타입이다.
- 로컬 저장소에도 신발 컬럼이 하나뿐이라 켤레를 나눌 자리가 없다.

즉 `userShoeId`는 직렬화 계약의 필드 추가가 아니라 **제품 기능**이다. 도입하려면 선행 조건이 있다.

1. 서버의 user-shoe 리소스 API (등록·조회·폐기)
2. 앱의 신발장 UI (보유 신발 등록, 다이어리 작성 시 켤레 선택)
3. 로컬 저장소 스키마 확장

> **회신안**: `userShoeId`는 v1.1 계약에서 제외하고 **별도 과제로 분리**한다. 위 1번(서버 API 설계)이 선행되면 클라이언트 작업을 함께 계획하겠다.

§3.4가 든 활용처(개별 누적거리·교체 주기)에는 동의하며, 기능으로 다룰 가치가 있다고 본다. 다만 지금 필드만 먼저 넣으면 항상 `null`이 나가므로 실익이 없다.

## 4. 확인 요청

1. **`Idempotency-Key` 제거를 수용할 수 있는가?** ([3.1장](#31-idempotency-key--v1에서-도입하지-않기를-제안))
   유지한다면 §2.3 충돌 해소 방식 (a) 413 재시도 예외 / (b) 키에 body 해시 포함 중 택일이 함께 필요하다.

2. **강수 지표를 `precipitationAmount`(mm)로 받을 수 있는가?**
   앱은 워크아웃 시각 기준 hourly 예보를 조회한다. 여기서 확실히 제공되는 강수 지표는 시간당 강수량(`precipitationAmount`, mm)이다. §3.5가 요청한 `precipitationIntensity`(mm/h)는 hourly 데이터에서의 가용성 확인이 필요하므로, 가능하면 전자로 계약하고 싶다.

3. **계약 버저닝을 URL 경로로 가르는 데 동의하는가?** ([3.2장](#32-schemaversion--보내지-않는-쪽을-제안))
   같은 엔드포인트에서 body의 `schemaVersion`으로 분기할 계획이라면 알려달라. 그 경우 필드를 채워 보내겠다.

4. **서버 저장과 로컬 저장의 순서, 오프라인 큐 요구 여부.**
   [요청 스키마 문서](./create-diary-request.md) 협의 때부터 미해소된 항목이다. 오프라인 작성이 요구사항이 아니라면 "서버 성공 후 로컬 저장"을 기본안으로 검토하고 있다.

추가로, [2.5장](#25-오류-코드-분기-4)에서 적었듯 **오류 응답 body의 형태**(`detail.code`의 JSON 경로와 타입)를 확정해주면 디코딩 타입을 맞추겠다.

## 6. 합의 후 진행

위 역제안과 확인 요청이 정리되면 [요청 스키마 문서](./create-diary-request.md)를 합의 내용으로 갱신하고, 그 문서를 계약의 단일 진실 소스로 유지한다.

§5(이 저장 구조로 제공 가능한 기능)에 나열된 항목은 이 회신안대로 진행해도 **모두 그대로 달성 가능**하다. 다만 두 가지는 조건이 붙는다.

- **현지 날짜 기준 집계** — `timeZone: null`인 기록은 서버 폴백값으로 계산하게 되므로 신뢰도 구분이 필요하다([3.3](#33-timezonesource-대신-timezone을-nullable로)).
- **사용자 신발별 누적거리·교체 알림** — `userShoeId` 선행 과제가 완료된 후에 가능하다([3.6](#36-usershoeid--전제-정정-후-별도-과제로-분리)).
